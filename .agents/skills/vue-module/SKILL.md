# 开发包

通过生成器建齐固定结构并绑定业务规则与测试，落实一处只装一件事和跟着已有印象走。

不要手工复制包目录或直接修改 `scaffold.json`；结构检查会核对登记表、跨包依赖和文件清单，未登记或多出的文件会让启动和打包失败。

## 用生成器创建骨架

```bash
npm run new:module -- 包名 --title 中文名
npm run new:page -- 包名 页面名 --title 中文名 --layout list --task "查找并打开业务对象"
npm run new:step -- 包名 步骤名 --action 动作编号 --rule R-01 --title 中文名
npm run docs
npm run check -- --quick --module 包名
```

1. **先写规则再生成步骤**。新建开发包后先在 `doc/包名/rules.md` 用行首 `R-01：正文` 或 `- R-01：正文` 写清操作者、权限、状态流转、异常与确认样例，在 `## 验证位置` 表按每条规则一行用反引号填写完整相对路径的 `.test.ts` 或 `.spec.ts`。未定规则标为"待确认"，具体数字带单位。`new:step` 要求指定所属动作与已声明的 `--rule` 编号，生成的骨架函数会主动失败，直到填入真实实现。
2. **按任务选定页面布局**。`new:page` 的 `--layout` 支持 `blank`、`list`、`form`、`detail`、`overview`（默认 `blank`），各自布局对照 [页面配方](../../../doc/ui-recipes.md)；用 `--task` 写明该页唯一用户任务。脚本只接受 `--title`、`--layout`、`--task`，缺值、未知参数或重复参数会在写文件前报错。模板仅建立静态起点，页面需接入真实查询与提交状态后再开放入口。

## 固定文件清单

| 文件 | 用途 |
| --- | --- |
| `module.ts` | 登记页面、动作、接口、依赖、文件清单及页面使用的 UI 组件名 |
| `public.ts` | 导出允许其他开发包调用的动作与公开接口 |
| `data.ts` | 定义输入、公开数据与步骤工作对象的 Zod 类型与中文说明 |
| `api.ts` | 声明同源接口方法、路径与响应校验结构 |
| `demo.ts` | 演示服务按接口编号返回的样例（静态 JSON 或处理函数），只供开发服务读取，业务代码不要导入 |
| `flow.ts` | 定义动作输入校验、字段中文说明、步骤顺序与权限标识 |
| `state.ts` | 创建供页面使用的只读任务状态，配置 `latest` 或 `submit` 并发策略 |
| `steps/` | 存放命名业务步骤 |
| `pages/` | 存放页面组件，只负责输入收集与状态渲染 |
| `tests/` | 按业务功能编写确认样例测试 |

## 编写规则与实现步骤

1. **守住依赖与导入边界**。包间调用只通过已声明依赖的 `public.ts`；业务代码只导入 `@/shared/public` 和 `@/shared/ui/public`，且页面注册表 `module.ts` 不提前静态导入计算步骤。
2. **严格声明动作输入与权限**。输入 schema 使用 `.strict()` 的 Zod 对象，字段写清用途和单位，敏感字段标记 `secret`。每个非公开动作在 `flow.ts` 声明自身 `permission`（生成器默认 `包名.run`，按实际业务改名），并在后端同步检查身份、组织和对象归属。
3. **写纯步骤并保持请求可信**。步骤只读取 `reads`、只写 `writes`，不原地修改传入的对象或数组，不通过 `return` 交出结果。所有网络请求走 `tools.request`：查询用 `latest` 模式自动取消旧请求，写入用 `submit` 模式。
4. **妥善处理失败与结果未知**。规则不满足直接抛错，由执行器统一拦截记录，不在页面或步骤里捕获后返回空数组或假成功。请求断线、超时或回包解析失败进入 `unknown` 状态，引导先查询真实结果，禁止自动重发。已有写入成功后后续步骤报错同样保留 `unknown`；同一动作发出的并行请求全部收尾后才确定步骤结果。登录状态切换或过期后，旧动作停止后续步骤，已发写入仍先查询核对。
5. **保持命名清晰且不写普通注释**。用函数名、类型、字段说明与测试表达意图，修改原因写进提交信息；只保留编译器指令与第三方许可。只把需单独追踪或定位的关键计算拆成步骤，简单格式化保持普通函数。

## 验收

1. 运行 `npm run docs && npm run check -- --module 包名`，确认依赖、结构、静态检查与确认样例全部通过；提交前运行完整检查，不把快速单包检查作为整仓结果。
2. 对照 `doc/包名/rules.md` 的规则编号与步骤 `rule` 属性逐项核对实现与测试；规则与代码冲突时先核对确认样例，再改实现。
