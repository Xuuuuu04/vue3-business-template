# 检查

```bash
npm run docs                         # 生成图与函数位置；改了步骤、页面、登记后先运行
npm run check -- --module 包名       # 只检查一个包：最快，不能证明几个包放在一起是对的
npm run check                        # 完整：结构、类型、单元样例、生成器
npm run test:browser                 # 浏览器行为（含主题对比度）；会启动开发服务
VITE_API_MODE=real npm run build     # 生产打包
```

怎么选：改一个包用 `--module`；改了 `src/shared`、`tools`、界面系统或不确定影响哪里，跑完整检查；整批交付和发布前，完整检查加浏览器检查都要跑。

## 框架保护记录

`framework.lock` 记录 `src/shared`、`src/app`、`tools`、框架测试和关键配置的摘要，防止被顺手改掉。启动、打包和 `npm run check` 都会核对它。

做业务时不要改这些文件。确实要改（比如新增界面组件），先看实际差异，写明用途和影响，再：

```bash
npm run docs
npm run framework -- --accept
```

`--accept` 只更新记录，不代表测试通过。改完之后还要跑检查。

## 写测试

- 预期结果来自 `doc/包名/rules.md` 里确认过的样例，不来自代码现在的输出。
- 一个业务功能一个测试文件，名字说明行为。测试名里写规则编号，如 `R-04：…`。
- 真实 bug、金额、权限、结果未知、并发这几类要留下可重复的测试。
- 行为测试优先按文字、角色和名称找元素；尺寸与滚动检查可使用公共组件专用的数据标记。

## 记录和汇报

检查结果写入本机 `var/checks`，包含源码指纹，代码改动后旧结果自动标为过期。单包检查不能写成全仓通过；没跑过的、失败的、跳过的都不能写成通过。演示服务和模拟测试不是真实后台验收。

## 画面检查

UI 改动按 `vue-ui` 的画面比较说明查看实际页面。检查代码声明的尺寸，也检查真实控件是否把行或面板撑高。公共样式变化要看相关组件、业务样板、窄屏和深色模式。

测试通过只说明所测行为和限制满足预期；画面是否清楚、是否达到用户给的参考，须另行比较与说明。不要以测试数量替代视觉验收。
